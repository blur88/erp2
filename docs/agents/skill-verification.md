# Verification at implementation and review entry points

## Plan before editing

1. Identify the [active implementation skill and its owner](#skill-ownership). Read the issue or spec and the repository's [Testing Guidelines](../../AGENTS.md#testing-guidelines) and [Change-Scoped Verification](../../AGENTS.md#change-scoped-verification-required-before-pr).
2. Search for existing regression tests and map them to each acceptance criterion. Record the test path and behavior it covers, any new or updated test needed, and any behavior that needs a real component to verify. For criteria with no applicable automated test, record the planned manual verification. In a delegated implementation, give each implementer the relevant criteria and plan, then have them confirm the plan in their worktree before editing.
3. Record the focused commands to use during implementation and the applicable final commands selected from the planned file changes. Follow [Verification waits](verification-waits.md) to choose local or CI execution for each applicable full suite. Use focused checks while editing and collect final verification on the review candidate. Revisit the plan when the changed files or criteria change.

For a Dockerfile package upgrade, the [committed regression test](../../scripts/__tests__/docker-image-packages.test.js) checks for the upgrade operation in the published image stage. The [Release validation CI step](../../.github/workflows/ci.yml) runs `npm run test:release`, which includes that test. A real build of the affected published stage verifies that the upgrade command executes successfully. Cite the build output that shows which packages changed when making a claim about package changes.

## Hand off review evidence

1. Identify the [active review skill and its dispatch step](#skill-ownership). Before dispatching either reviewer, pin the starting or base SHA and the reviewed commit SHA. Prepare one shared snapshot containing the issue or spec reference and its acceptance criteria, both SHAs, the PR URL when available, and the evidence for that reviewed commit. For each applicable verification command give the exact command and working directory, exit status or CI conclusion, actual result, and links or accessible logs when available. List pending checks and evidence gaps explicitly. Follow [Verification waits](verification-waits.md) to collect results from the same completed runs for both reviewers.
2. If mandatory evidence is pending or missing, defer the affected assessment or label both assignments **preliminary, code-only** and keep the affected criteria **Unverified**. For a preliminary review, still send the snapshot with the gaps listed. Send the same snapshot verbatim or as the same fixed reference to both reviewers, alongside their axis-specific briefs.
3. In **each** assignment, require the reviewer to read [Acceptance-criterion evidence in reviews](../../CODING_STANDARDS.md#acceptance-criterion-evidence-in-reviews) before assessment and report the **Implemented**, **Demonstrated**, or **Unverified** verdicts for every applicable criterion, citing evidence and identifying gaps. Preserve those verdicts separately in the Standards and Spec reports.
4. Before reporting, recheck the reviewed SHA and the remaining evidence. If the head moves, discard verification claims tied to the previous SHA and send both reviewers a refreshed snapshot for the new SHA. If additional evidence arrives for the same SHA, send both reviewers the updated snapshot and refresh both assessments. Report complete verification only when the required evidence for the reviewed commit supports it.

## Skill ownership

Use the loaded skill's source path to identify its owner. The plugin-qualified `mattpocock-skills:implement` and `mattpocock-skills:implement-spec` invocations load plugin-managed skills. In the resolved `code-review` skill, apply the handoff before the step that spawns the two reviewers. Copies under `.agents/skills/` are ignored in this repository. Apply this Git-tracked handoff through [AGENTS.md](../../AGENTS.md#workflow-entry-points) alongside the loaded skill. Maintain the ERP workflow in this repository and leave shared and upstream skill installations untouched.
