# Design: Transaction-Led, Admin-Overridable Architecture (Issue #393)

## Overview

Standardize the editing lifecycle and access control for four child transaction modules: Goods Received Notes (GRN), Vendor Payments (VP), Invoices, and Customer Payments. Records in these modules are generated by the parent PO/SO workflow. Manual creation and deletion are Admin-only emergency escape hatches. Parent orders lock their line items once money or stock has moved.

## Section 1: Access Control (Admin-Only Manual Create/Delete)

Add `@Roles(UserRole.ADMIN)` to the following controller methods:

| Module | Protected endpoints |
|---|---|
| GRN | `POST /` (create), `DELETE /:id` (soft), `DELETE /:id/permanent` |
| Vendor Payment | `POST /` (create), `DELETE /:id` (soft), `DELETE /:id/permanent` |
| Invoice | `DELETE /:id` (soft), `DELETE /:id/permanent` — POST already removed in PR #388 |
| Customer Payment | `POST /` (create), `DELETE /:id` (soft) |

Standard users trigger these records via PO/SO workflow. Non-admins hitting these endpoints receive a 403. No frontend changes required — manual create/delete buttons are already absent from list pages.

## Section 2: PurchaseOrderLifecycleService (New)

Create `backend/src/modules/purchasing/services/purchase-order-lifecycle.service.ts`, mirroring the existing `SalesOrderLifecycleService` pattern.

### Item-lock check
Called before any PO line item update:
- Block if `paidAmount > 0` (vendor payment exists)
- Block if any associated GRN has `status == RECEIVED`
- Header fields (dates, notes, supplier) bypass this check and always update freely

### Soft-delete guard
Called before PO soft-delete:
- Block if `paidAmount > 0` → error: "Unpay all vendor payments before deleting"
- Block if any GRN has `status == RECEIVED` → error: "Return all goods before deleting"
- If clear: soft-delete PO, then cascade soft-delete all associated GRNs and VPs with the same `deletedAt` timestamp

### Permanent-delete guard
Called before PO hard-delete:
- Block if any stock movements exist in DB referencing this PO's GRNs
- Block if any vendor payments exist in DB for this PO
- If clear: hard-delete PO and all associated GRNs, VPs, and their items

### Child sync
Called when PO items or header are saved (only if not locked):
- Sync items (product, qty, price) to the associated DRAFT GRN
- Sync header (supplier, dates, notes) to the associated DRAFT GRN and any UNPAID vendor payments
- Skip any GRN already in RECEIVED status

`PurchaseOrderService` delegates lock checks and cascade operations to this lifecycle service.

## Section 3: SalesOrderLifecycleService (Extend Existing)

The existing `SalesOrderLifecycleService` already handles soft-delete guards. Extensions:

### Item-lock check (new method)
Called before any SO line item update:
- Block if `paidAmount > 0`
- Block if `isFulfilled == true`
- Header fields (dates, notes, customer) always update freely

### Soft-delete guard
Already exists — no change needed.

### Permanent-delete guard (extend)
Match PO pattern:
- Block if any stock movements exist in DB referencing this SO's fulfillments
- Block if any customer payments exist in DB for this SO
- If clear: hard-delete SO, associated invoices, payments, and their items

### Child sync (extend)
Called when SO items or header are saved (only if not locked):
- Sync items (product, qty, price) to the associated DRAFT invoice using existing `syncItemsFromSalesOrder()`
- Extend to also sync header (customer, dates, notes) to DRAFT invoice and UNPAID customer payments
- Skip invoices already in PAID or PARTIAL_PAID status

## Section 4: Frontend Archive Pattern

Four list pages become read-only archives. Changes are minimal — workspace cards are already read-only.

### GRN & Vendor Payment pages
- Context header already has "Navigate to PO" link — no change needed
- Remove any soft-delete/restore action buttons from toolbar if present
- `secondaryAction` remains "View Deleted" only

### Invoices & Customer Payments pages
- Verify context headers have "Navigate to SO" link — add if missing
- Toolbar: Print + Navigate to Parent only
- `secondaryAction` remains "View Deleted" only

### PO & SO pages
- Add inline lock indicator on items table when locked: subtle banner — "Items are locked — unpay or return goods to edit"
- Header fields remain editable with no lock indicator
- No new dialogs or pages required

## Section 5: Testing

### Backend (Jest)
- `PurchaseOrderLifecycleService` — test each guard: blocks when `paidAmount > 0`, blocks when GRN is RECEIVED, allows when both clear; test cascade soft-delete sets same timestamp on GRN and VP; test permanent-delete blocks when stock movements exist
- `SalesOrderLifecycleService` — extend existing spec: test item-lock blocks when `paidAmount > 0` or `isFulfilled`; test permanent-delete guard; test header sync skips PAID invoices
- Controller role guards — verify 403 for non-admin on protected endpoints

### Frontend (Vitest)
- No new component tests needed
- Update existing PO/SO workspace tests if they assert on item editability

### Manual smoke test checklist
1. Standard user cannot POST/DELETE GRN, VP, Invoice, Payment — gets 403
2. Admin can manually create/delete all four
3. PO with paid VP → line item edit blocked, header edit allowed
4. PO with RECEIVED GRN → line item edit blocked
5. PO soft-delete blocked until unpaid + returned; cascades to GRN and VP with same timestamp
6. PO permanent delete blocked if stock movements or payments in DB
7. SO same as PO equivalents
8. Editing PO items syncs to DRAFT GRN items and header

## Decisions & Constraints

- **Lock scope:** Items only (not header fields) — header edits carry no financial risk and blocking them causes unnecessary reversal churn
- **Stock reversal on soft-delete:** Not automatic — user must manually Return Goods and Unpay via PO/SO page before soft-delete is allowed; stock reversal happens as part of those manual steps
- **Permanent delete:** Only allowed if no stock movements and no payments exist in DB (clean slate)
- **Cascade consistency:** PO and SO follow identical soft-delete and permanent-delete guard patterns
- **Frontend:** Workspace cards are already read-only; no new dialogs needed
- **Approach:** Lifecycle service pattern (Option B) — extends existing `SalesOrderLifecycleService`, creates matching `PurchaseOrderLifecycleService`
