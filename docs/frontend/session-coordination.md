# Session coordination

[Issue #1548](https://github.com/blur88/erp2/issues/1548) introduces the shared Session record. The overall design is [spec #1546](https://github.com/blur88/erp2/issues/1546); the [decision record](https://github.com/blur88/erp2/issues/1345#issuecomment-6505446834) governs it. This document owns the accepted limits for that design.

## Current implementation

The [coordinator](../../frontend/src/services/session/coordinator.ts) opens one shared IndexedDB record. A last-ended-Session marker invalidates login attempts begun before a matched End browser Session, including attempts begun while signed out. It is compared atomically at sign-in; valid concurrent sign-ins remain last-save-wins. Each sign-in gives it a new id from `crypto.getRandomValues`. Redux auth is an in-memory view. Startup deletes `persist:erp-app` without reading or migrating it, requiring an upgrade sign-in. Startup also deletes the temporary `persist:erp-notifications` key without reading it. Notifications are in-memory only; redux-persist is removed.

Every request through the Axios transport re-reads the shared record before attaching credentials. A tab that missed a change therefore cannot use its old token on its next request. A refresh saves only while both the Session id and the refresh token tried still match. The coordinator's **End browser Session** operation deletes only the matching record; deletion after a refresh 401 also matches both the Session id and refresh token tried. This local deletion does not itself revoke server credentials or end Sessions on other devices; backend **Sign out** is a separate best-effort action. Rate-limit outcome records use `refresh-failure:<holder>:<expires>` keys; cleanup deletes them by Session id. They preserve a 429 for requests using the same Session and refresh token that started before the attempt settled, then are deleted atomically when the Session ends or a newer refresh succeeds. Requests started after the 429 settles may refresh. Single-field writes occur inside one readwrite transaction and leave other fields untouched. Activity updates keep the later timestamp.

Failure to open storage at startup or sign-in reports “This browser's storage is unavailable” and establishes no Session. A required runtime read or write failure rejects the operation. There is no in-memory storage fallback or automatic reopening after a runtime failure.

[T2 (#1549)](https://github.com/blur88/erp2/issues/1549) installs BroadcastChannel hints and `visibilitychange`, `pageshow` and `focus` listeners. Each hint or resume queues a shared-record read; requests finish their own read before sending. A Session-id change first blocks the old Session and clears auth, reconciliation drafts, notifications and every RTK Query cache, then adopts the new Session. Observing a deletion only clears local auth and state and fully navigates to `/login`; it never initiates another End browser Session, calls backend Sign out or rebroadcasts. Successful HTTP responses re-check their originating Session before returning data. Disposal detaches the listeners and closes the channel. There is no periodic Session polling. Refresh is serialized by a 15-second IndexedDB lock; waiting tabs recheck on hints and every 250 ms and reuse a newer access token. A refresh 429 preserves the Session and releases the lock. A timeout or a successful response that could not be saved leaves the lock to expire. Network errors and 5xx responses also leave it to expire: this is an inference from the risk that rotation may have happened, not a rule stated in [T4 (#1551)](https://github.com/blur88/erp2/issues/1551). After a 401 with an unchanged token following an expired-lock takeover, the holder waits up to 30 seconds, re-reading on BroadcastChannel hints and every 250 ms while retaining the lock subject to expiry. A newer token in the same Session is revalidated through a matched lock acquisition before reuse; deletion triggers local cleanup; a different Session id discards the operation. At the deadline, the coordinator uses the End browser Session operation only when the original Session id and refresh token still match. Reconciliation drafts carry the saving Session id; restore deletes a draft if that id is missing or differs from the current Session.

[T7 (#1553)](https://github.com/blur88/erp2/issues/1553) adds a throttled activity write and shared idle check. Activity writes are immediate after a quiet minute and throttled to one per minute afterwards; “Stay Logged In” requires its write to succeed. The warning and End browser Session decisions re-read shared activity, and idle deletion atomically checks the Session id, `rememberMe`, and the configured idle timeout (12 h by default). Runtime `window.__ENV__.SESSION_IDLE_TIMEOUT_MS` defaults to 12 hours; the session browser harness sets its 120-second value in `tests/session/compose.yml`, which also lifts the frontend read-only setting for the test stack. A write failure prevents the user action and is surfaced to the user.

## Accepted limits

- **Delivered messages.** The design's one-second End browser Session bound applies to a running tab after BroadcastChannel delivery. A missed message may leave stale content visible until reconciliation. Requests always check shared storage. Coordinator tests cover delivered hints; Chromium verification is recorded in the [T7.5 PR](https://github.com/blur88/erp2/pull/1622).
- **Lost refresh responses and paused holders.** If the server rotates a refresh token and its response is lost, the Session can be lost in every tab. A holder delayed beyond its recovery window can also lose the Session: recovery waits up to 30 seconds after a takeover 401, following the lock's 15-second expiry, for a nominal 45 seconds from acquisition. This is not a precise frozen-tab cutoff; request duration and browser scheduling can extend it. The 10-second client timeout does not mean the server stopped processing.
- **Mixed versions during rollout.** Old tabs do not participate in coordination. Until reloaded, they can produce refresh conflicts or inconsistent End browser Session behavior. Disruption is not limited to one End browser Session.
- **Issued access tokens.** The earlier decision record listed tokens remaining valid until expiry as a limitation delegated to [#1545](https://github.com/blur88/erp2/issues/1545). That follow-up has since implemented per-user token-version revocation; see the [revocation ADR](../adr/0001-sign-out-revokes-by-token-version.md). The old expiry limitation is therefore historical, not a guarantee of current behavior. The discrepancy with #1548 is [recorded on #1345](https://github.com/blur88/erp2/issues/1345#issuecomment-6528687585). Browser coordination does not replace server revocation, and a failed best-effort backend logout cannot guarantee that server Sessions ended.
- **Notifications.** History is per tab and lost on reload. The upgrade removes the old combined auth/notification record without migration.
- **Browser verification.** Unit tests use `fake-indexeddb` and do not prove browser suspension or storage durability. On merged `main` head `6f62424ede074f9c0c7954bf129fdabb53653eab`, `set -a; . tests/session/.env.local; set +a; tests/session/run.sh` passed in Chromium over plain HTTP at LAN IP `10.1.1.34`; its raw output was not preserved, and the terminal summary recorded End browser Session propagation at 359 ms. This is local HTTP test evidence, not production evidence. The test stack used `JWT_ACCESS_TOKEN_EXPIRY=8s`, `SESSION_IDLE_TIMEOUT_MS=120000`, and a generated NGINX config with `login_limit=120r/m` for the full cross-tab run; the separate 429 check restored the default `login_limit=5r/m`. Five full Chromium-over-HTTP runs preserved in [PR #1622 comment 6603850529](https://github.com/blur88/erp2/pull/1622#issuecomment-6603850529) passed shared Session, reload restore, concurrent refresh, takeover recovery and loss, End browser Session propagation, in-flight refresh, draft cleanup, idle behavior, user switch, and the default-limit refresh 429; their propagation measurements were 424, 402, 367, 441 and 423 ms (runs 1 through 5). The suspended-tab resume PASS and 387 ms End browser Session propagation result come from the Chromium-over-HTTP run preserved in the [PR #1638 body at head `1cf0a270d`](https://github.com/blur88/erp2/pull/1638). Firefox, Safari, mobile browsers and natural sleep/freeze remain unverified. No production host exists.
