# Session coordination

[Issue #1548](https://github.com/blur88/erp2/issues/1548) introduces the shared Session record. The overall design is [spec #1546](https://github.com/blur88/erp2/issues/1546); the [decision record](https://github.com/blur88/erp2/issues/1345#issuecomment-6505446834) governs it. This document owns the accepted limits for that design.

## Current implementation

The [coordinator](../../frontend/src/services/session/coordinator.ts) opens one shared IndexedDB record. A last-ended-Session marker invalidates login attempts begun before a matched sign-out, including attempts begun while signed out. It is compared atomically at sign-in; valid concurrent sign-ins remain last-save-wins. Each sign-in gives it a new id from `crypto.getRandomValues`. Redux auth is an in-memory view. Startup deletes `persist:erp-app` without reading or migrating it, requiring an upgrade sign-in. Startup also deletes the temporary `persist:erp-notifications` key without reading it. Notifications are in-memory only; redux-persist is removed.

Every request through the Axios transport re-reads the shared record before attaching credentials. A tab that missed a change therefore cannot use its old token on its next request. A refresh saves only while both the Session id and the refresh token tried still match. Sign-out deletes only the matching Session; refresh-failure deletion also matches the token tried. Single-field writes occur inside one readwrite transaction and leave other fields untouched. Activity updates keep the later timestamp.

Failure to open storage at startup or sign-in reports “This browser's storage is unavailable” and establishes no Session. A required runtime read or write failure rejects the operation. There is no in-memory storage fallback or automatic reopening after a runtime failure.

[T2 (#1549)](https://github.com/blur88/erp2/issues/1549) installs BroadcastChannel hints and `visibilitychange`, `pageshow` and `focus` listeners. Each hint or resume queues a shared-record read; requests finish their own read before sending. A Session-id change first blocks the old Session and clears auth, reconciliation drafts, notifications and every RTK Query cache, then adopts the new Session. Observing a deletion only cleans up locally and fully navigates to `/login`; it never deletes, calls backend logout or rebroadcasts. Successful HTTP responses re-check their originating Session before returning data. Disposal detaches the listeners and closes the channel. There is no periodic Session polling. Refresh is serialized by a 15-second IndexedDB lock; waiting tabs recheck on hints and every 250 ms and reuse a newer access token. A refresh 429 preserves the Session and releases the lock. Until T5 adds recovery, a 401 after taking over an expired lock preserves the Session and leaves the lock to expire. Shared idle handling and Session-tagged drafts follow in later tickets under #1345.

## Accepted limits

- **Delivered messages.** The design's one-second sign-out bound applies to a running tab after BroadcastChannel delivery. A missed message may leave stale content visible until reconciliation. Requests always check shared storage. Coordinator tests cover delivered hints; the real-browser timing measurement remains T3 work.
- **Lost refresh responses and paused holders.** If the server rotates a refresh token and its response is lost, the Session can be lost in every tab. The 10-second client timeout does not mean the server stopped processing. T5 will add a recovery wait; its planned nominal window is 45 seconds, not a precise frozen-tab cutoff, because request duration and browser scheduling can extend it. Refresh coordination is not considered usable until T5 is also on the integration branch.
- **Mixed versions during rollout.** Old tabs do not participate in coordination. Until reloaded, they can produce refresh conflicts or inconsistent sign-out. Disruption is not limited to one sign-out.
- **Issued access tokens.** The earlier decision record listed tokens remaining valid until expiry as a limitation delegated to [#1545](https://github.com/blur88/erp2/issues/1545). That follow-up has since implemented per-user token-version revocation; see the [revocation ADR](../adr/0001-sign-out-revokes-by-token-version.md). The old expiry limitation is therefore historical, not a guarantee of current behavior. The discrepancy with #1548 is [recorded on #1345](https://github.com/blur88/erp2/issues/1345#issuecomment-6528687585). Browser coordination does not replace server revocation, and a failed best-effort backend logout cannot guarantee that server Sessions ended.
- **Notifications.** History is per tab and lost on reload. The upgrade removes the old combined auth/notification record without migration.
- **Browser verification.** Unit tests use `fake-indexeddb` and do not prove browser suspension or storage durability. The earlier spike used Chromium over HTTP at a LAN IP; it did not run the application. The real application's LAN HTTP browser run belongs to [T3 (#1550)](https://github.com/blur88/erp2/issues/1550). No production host exists and these are not production results.
