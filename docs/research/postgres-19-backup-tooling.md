# PostgreSQL 19 backup and restore tooling

Research input for [#2067](https://github.com/blur88/erp2/issues/2067) ("Redesign Backup & Restore before production"). Facts only. The design decision is left to the maintainer.

**Checked on:** 2026-11-27 to 2026-11-28. Versions checked: PostgreSQL 19.0 (released 2026-11-19), pgBackRest 2.60.1 (2026-11-16), WAL-G v3.0.10 (2026-11-17), Barman 3.21.0 (2026-11-17), Redis 8.6.8 (`redis.conf` at tag `8.6.8`).

Lines marked **[local test]** come from running `postgres:19.0-alpine3.24` (image ID `44b6eb1a664b`) on the dev host on 2026-11-28. They are observations, not documentation.

## Summary

PostgreSQL 19 ships every tool a single-host design needs. `pg_dump`/`pg_restore` produce logical backups. `pg_basebackup` produces physical backups, incremental since 17, combined with `pg_combinebackup` and checked with `pg_verifybackup`. WAL archiving plus `restore_command` gives point-in-time recovery (PITR). PG19 changes little here: `pg_verifybackup` and `pg_waldump` can read WAL from tar archives, and pre-19 `pg_dump` output may not load into a PG19 server. A PG19 client has to be version-matched. Alpine 3.24 ships only up to `postgresql18-client`, and `postgresql19-client` exists only in edge/testing. The official `postgres:19.0-alpine3.24` image does contain the full PG19 client and backup binary set, and the current runbook already uses it as a one-off sidecar. That image's default `pg_hba.conf` rejects replication connections from other containers, so `pg_basebackup` from a sidecar requires an hba change **[local test]**. All three third-party tools are actively maintained. None of them states support for PostgreSQL 19.0 GA in a release. pgBackRest documents support up to 19rc2. WAL-G added PG19 to its CI matrix on its development branch after its latest release. Barman's release notes and docs don't mention 19.

## 1. Built-in PostgreSQL 19 tools

The PG19 docs name three approaches: SQL dump, file-system-level backup and continuous archiving ([backup.html](https://www.postgresql.org/docs/19/backup.html)).

### pg_dump / pg_restore / pg_dumpall

- **Formats.** plain (`p`), custom (`c`), directory (`d`) and tar (`t`). The custom and directory formats "allow for selection and reordering of all archived items, support parallel restoration, and are compressed by default". The tar format is uncompressed ([app-pgdump](https://www.postgresql.org/docs/19/app-pgdump.html)).
- **Parallelism.** `pg_dump -j` works only with the directory format ([app-pgdump](https://www.postgresql.org/docs/19/app-pgdump.html)). `pg_restore -j` accepts custom and directory archives only, from a regular file or directory, not a pipe or stdin, and cannot be combined with `--single-transaction` ([app-pgrestore](https://www.postgresql.org/docs/19/app-pgrestore.html)).
- **Consistency.** pg_dump "makes consistent exports even if the database is being used concurrently" and does not block readers or writers ([app-pgdump](https://www.postgresql.org/docs/19/app-pgdump.html)).
- **Scope.** pg_dump covers one database and no roles or tablespaces. `pg_dumpall --globals-only` dumps those ([backup-dump](https://www.postgresql.org/docs/19/backup-dump.html)). pg_dumpall in 19 documents plain SQL output only, with no `-F` option ([app-pg-dumpall](https://www.postgresql.org/docs/19/app-pg-dumpall.html)).
- **Version rule** ([app-pgdump](https://www.postgresql.org/docs/19/app-pgdump.html)): pg_dump can dump older servers (back to 9.2), but "cannot dump from PostgreSQL servers newer than its own major version; it will refuse to even try". Output can be expected to load into newer servers, but loading into an older major version is not guaranteed. `--quote-all-identifiers` is recommended for cross-version cases.
- **PG19 change.** `standard_conforming_strings` is now always on. "Dumps created using pre-PostgreSQL 19 versions of pg_dump or pg_dumpall, and using standard_conforming_strings = off, will not properly load into PostgreSQL 19". Users should dump with the 19 tools ([release-19](https://www.postgresql.org/docs/19/release-19.html)). Also new in 19: "Allow pg_dump to include restorable extended statistics". `pg_read_all_data` can now read large objects, so non-superusers can run pg_dump ([release-19](https://www.postgresql.org/docs/19/release-19.html)).
- **Statistics.** `--statistics` dumps optimizer statistics, `--no-statistics` is the default, and running `ANALYZE` after a restore is still recommended ([app-pgdump](https://www.postgresql.org/docs/19/app-pgdump.html)). These options were added in 18 ([release-18](https://www.postgresql.org/docs/18/release-18.html)).
- **Restore safety options.** `--exit-on-error`, `--single-transaction` (not with `--create` or `-j`), `--transaction-size`, and `-l`/`-L` to list a table of contents and restore only selected items ([app-pgrestore](https://www.postgresql.org/docs/19/app-pgrestore.html)).

### pg_basebackup, incremental backup, pg_combinebackup

- **Scope.** A physical copy of the whole cluster: "it is not possible to back up individual databases" ([app-pgbasebackup](https://www.postgresql.org/docs/19/app-pgbasebackup.html)).
- **Self-contained backups.** With `-X fetch` or `-X stream` (the default), the result is "a completely standalone backup" that needs no WAL archive. Plain or tar format, client- or server-side gzip/lz4/zstd compression. A backup manifest with CRC32C checksums is written by default ([app-pgbasebackup](https://www.postgresql.org/docs/19/app-pgbasebackup.html)).
- **Requirements.** A user with REPLICATION (or superuser), a `pg_hba.conf` entry that permits the replication connection, and enough `max_wal_senders`. "pg_basebackup works with servers of the same or older major version" ([app-pgbasebackup](https://www.postgresql.org/docs/19/app-pgbasebackup.html)).
- **Incremental backups (17+).** `pg_basebackup --incremental=<prior backup_manifest>` needs server 17+. "An incremental backup cannot be used directly". It must first be combined with `pg_combinebackup` ([app-pgbasebackup](https://www.postgresql.org/docs/19/app-pgbasebackup.html)). The server needs WAL summaries covering the interval since the prior backup, or "the incremental backup will fail" ([continuous-archiving](https://www.postgresql.org/docs/19/continuous-archiving.html)). Summaries come from `summarize_wal` (default `off`) and are kept for `wal_summary_keep_time` (default 10 days) ([runtime-config-wal](https://www.postgresql.org/docs/19/runtime-config-wal.html)).
- **Chain tracking is manual.** "PostgreSQL has no built-in mechanism to figure out which backups are still needed as a basis for restoring later incremental backups. You must keep track of the relationships … on your own" ([continuous-archiving](https://www.postgresql.org/docs/19/continuous-archiving.html)). `pg_combinebackup` checks that the chain is legal "not that each individual backup is intact; for that, use pg_verifybackup". It also does not recompute page checksums if the checksum state changed within the chain ([app-pgcombinebackup](https://www.postgresql.org/docs/19/app-pgcombinebackup.html)).
- **Changes in 18 and 19.** 18 added `pg_combinebackup --link` and `pg_verifybackup` support for tar-format backups ([release-18](https://www.postgresql.org/docs/18/release-18.html)). 19 adds a `backup_type` (full/incremental) column to `pg_stat_progress_basebackup`. The PG19 notes list no other incremental-backup or `pg_combinebackup` changes ([release-19](https://www.postgresql.org/docs/19/release-19.html)).
- **[local test]** With `summarize_wal=on`, the sequence full backup, incremental backup, `pg_combinebackup`, and `pg_verifybackup` on all three outputs succeeded on PG19.0 from a sidecar container. A replication hba line had to be added first (see §2).

### WAL archiving and PITR

- **Enabling it** needs `wal_level` of `replica` or higher, `archive_mode=on`, and either `archive_command` or `archive_library`. The archive command must "return zero exit status if and only if it succeeds" and should refuse to overwrite an existing archive file ([continuous-archiving](https://www.postgresql.org/docs/19/continuous-archiving.html)). The bundled `basic_archive` module is an example that "can serve as a starting point" ([basic-archive](https://www.postgresql.org/docs/19/basic-archive.html)).
- **Failure mode.** Failed archiving makes WAL pile up. "If the file system containing pg_wal/ fills up, PostgreSQL will do a PANIC shutdown", so archiving must be monitored ([continuous-archiving](https://www.postgresql.org/docs/19/continuous-archiving.html)).
- **What PITR needs.** A base backup plus an unbroken WAL sequence back to the start of that backup. The docs advise setting up and testing archiving before the first base backup, keeping several backup sets, and backing up config files separately ([continuous-archiving](https://www.postgresql.org/docs/19/continuous-archiving.html)). `archive_timeout` of "a minute or so" is usually reasonable for low-traffic systems ([continuous-archiving](https://www.postgresql.org/docs/19/continuous-archiving.html)).
- **Recovery.** Create `recovery.signal` and set `restore_command`, which must return nonzero on failure ([continuous-archiving](https://www.postgresql.org/docs/19/continuous-archiving.html)). Targets are `recovery_target=immediate`, `_time`, `_xid`, `_lsn` and `_name`. `recovery_target_inclusive` defaults to on, `recovery_target_timeline` to `latest`, and `recovery_target_action` to `pause` ([runtime-config-wal](https://www.postgresql.org/docs/19/runtime-config-wal.html)).
- **PG19 changes.** A new `pg_stat_recovery` view. `pg_waldump` and `pg_verifybackup` can read WAL inside tar archives (`--wal-path`, which replaces the deprecated `--wal-directory`). The notes list no `archive_command`/`archive_library` or PITR changes ([release-19](https://www.postgresql.org/docs/19/release-19.html)).

### pg_verifybackup, pg_amcheck and data checksums

- **pg_verifybackup** checks a backup against its manifest: files present, sizes, checksums, and the WAL needed for recovery. It reads both plain and tar formats. It "does not and cannot include every check which will be performed by a running server", and the docs say "you should still perform test restores" ([app-pgverifybackup](https://www.postgresql.org/docs/19/app-pgverifybackup.html)). It does not apply to pg_dump output.
- **pg_amcheck** checks heap tables, TOAST, sequences, materialized views and **B-tree indexes only**. Other relation types "are silently skipped". It needs the `amcheck` extension (`--install-missing`). The `--parent-check` and `--rootdescend` options take locks that block writes ([app-pgamcheck](https://www.postgresql.org/docs/19/app-pgamcheck.html)). The `amcheck` extension gained `gin_index_check()` in 18 ([release-18](https://www.postgresql.org/docs/18/release-18.html)).
- **Data checksums.** On by default since 18. `pg_upgrade` requires matching checksum settings ([release-18](https://www.postgresql.org/docs/18/release-18.html), [app-initdb 19](https://www.postgresql.org/docs/19/app-initdb.html)). PG19 adds only AVX2 checksum computation ([release-19](https://www.postgresql.org/docs/19/release-19.html)). **[local test]** A fresh `postgres:19.0-alpine3.24` cluster reports `data_checksums=on`, `summarize_wal=off`, `wal_level=replica`, `archive_mode=off` and `max_wal_senders=10`.

**The official image as a sidecar.** The docker-library `19/alpine3.24` Dockerfile builds 19.0 from source on `alpine:3.24` and runs `make install-world-bin` and `make -C contrib install`. It declares `VOLUME /var/lib/postgresql` with `PGDATA /var/lib/postgresql/19/docker` and installs no third-party backup tool ([Dockerfile](https://github.com/docker-library/postgres/blob/master/19/alpine3.24/Dockerfile)).

**[local test]** `/usr/local/bin` in `postgres:19.0-alpine3.24` contains `pg_dump`, `pg_dumpall`, `pg_restore`, `psql`, `pg_basebackup`, `pg_combinebackup`, `pg_verifybackup`, `pg_amcheck`, `pg_receivewal`, `pg_waldump`, `pg_walsummary`, `pg_archivecleanup`, `pg_checksums` and `pg_upgrade` (`pg_dump --version` prints 19.0). The interim runbook already runs these through `docker run --rm --network … --entrypoint …` ([runbook](../deployment/POSTGRES_19_MAJOR_UPGRADE_RUNBOOK.md)).

**Replication access.** The entrypoint appends only `host all all all <auth>` to `pg_hba.conf` ([docker-entrypoint.sh](https://github.com/docker-library/postgres/blob/master/19/alpine3.24/docker-entrypoint.sh)). The sample's `replication` lines cover only local sockets and loopback. **[local test]** `pg_basebackup` from a second container on the same network failed with `no pg_hba.conf entry for replication connection`. It worked after adding `host replication all all scram-sha-256`. The PG19 hba docs define `replication` as matching physical replication connections ([auth-pg-hba-conf](https://www.postgresql.org/docs/19/auth-pg-hba-conf.html)). `pg_dump` needs no such change.

## 3. Third-party tools

### pgBackRest

- **PG19 support: GA unconfirmed.** 2.59.0 added "PostgreSQL 19beta2 support", 2.59.1 beta3, and 2.59.2 beta4 ([releases](https://github.com/pgbackrest/pgbackrest/releases)). The 2.60.0 and 2.60.1 news items say "19rc1/19rc2 is supported by v2.59.2 and later" ([news.xml](https://github.com/pgbackrest/pgbackrest/blob/main/doc/xml/news.xml)). In the 2.60.1 source, `PG_VERSION_MAX` is `PG_VERSION_19` ([version.auto.h](https://github.com/pgbackrest/pgbackrest/blob/release/2.60.1/src/postgres/version.auto.h)). No release after 19.0 GA (2026-11-19) existed when checked.
- **Deploy shape.** Repository types are `posix` (local disk), `cifs`, `s3`, `azure`, `gcs` and `sftp`. A remote PostgreSQL host is reached over SSH or the pgBackRest TLS server ([configuration](https://pgbackrest.org/configuration.html)). WAL archiving uses `archive_command = 'pgbackrest --stanza=… archive-push %p'` on the PostgreSQL host, and local and remote versions "must match exactly" ([user guide](https://pgbackrest.org/user-guide.html)). So pgBackRest must run where PostgreSQL can execute it, which here means inside the postgres container. That is an inference from the documented `archive_command`. No official container image was found on pgbackrest.org.
- **Alpine packages.** v3.24/community ships **2.58.0** (2026-01-20, before any PG19 support). edge/community ships 2.60.1 ([v3.24](https://pkgs.alpinelinux.org/packages?name=pgbackrest&branch=v3.24&arch=x86_64), [edge](https://pkgs.alpinelinux.org/packages?name=pgbackrest&branch=edge&arch=x86_64)).
- **Backups and retention.** full, diff and incr (default incr), plus opt-in block incremental (`repo-block`). Retention is set by `repo-retention-full` (count or days), `-diff` and `-archive`, and `expire` runs after each backup ([command](https://pgbackrest.org/command.html), [configuration](https://pgbackrest.org/configuration.html)).
- **PITR.** `restore --type` accepts `time`, `xid`, `lsn`, `name` and `immediate`, plus `--delta` ([command](https://pgbackrest.org/command.html)).
- **Encryption.** `repo-cipher-type=aes-256-cbc` ([configuration](https://pgbackrest.org/configuration.html)).
- **Verification.** `check` "validates that pgBackRest and the archive_command setting are configured correctly". `verify` "determines if the backups and archives in a repository are valid" ([command](https://pgbackrest.org/command.html)). Since 2.60.0, restore errors on invalid page checksums by default (`checksum-page-error`) ([news.xml](https://github.com/pgbackrest/pgbackrest/blob/main/doc/xml/news.xml)).
- **Licence and activity.** MIT ([LICENSE](https://github.com/pgbackrest/pgbackrest/blob/main/LICENSE)). Five releases between 2026-08-17 and 2026-11-16.

### WAL-G

- **PG19 support: unconfirmed in a release.** The v3.0.10 notes don't mention 19, and its Makefile tests `PG_VERSIONS ?= 14 15 16 17 18`. Commit `d49e3b16e` on master (2026-11-24, "test(pg): run the integration suite on PostgreSQL 19") adds 19 to the matrix, after the release ([Makefile@v3.0.10](https://github.com/wal-g/wal-g/blob/v3.0.10/Makefile), [Makefile@master](https://github.com/wal-g/wal-g/blob/master/Makefile)).
- **Deploy shape.** A single Go binary that pushes to remote storage or a local path (`WALG_FILE_PREFIX`) ([STORAGES.md](https://github.com/wal-g/wal-g/blob/master/docs/STORAGES.md)). There are two modes. It can run on the DB host with filesystem access, which enables delta and partial restore. Or it can stream over the `BASE_BACKUP` protocol, where "Delta backup currently is not implemented" ([PostgreSQL.md](https://github.com/wal-g/wal-g/blob/master/docs/PostgreSQL.md)). WAL goes through `wal-push` (`archive_command`) and `wal-fetch` (`restore_command`). Release binaries are Ubuntu 20.04/22.04/24.04 builds, with no Alpine/musl asset ([v3.0.10 assets](https://github.com/wal-g/wal-g/releases/tag/v3.0.10)). There is no Alpine package in v3.24 or edge.
- **Incremental and retention.** Delta backups via `WALG_DELTA_MAX_STEPS` (default 0, disabled). `delete retain|before|everything|target`, dry-run unless `--confirm`. The docs warn that after a major upgrade, `retain` can delete **new** backups unless `--use-sentinel-time` is used ([docs/README.md](https://github.com/wal-g/wal-g/blob/master/docs/README.md)).
- **Encryption.** libsodium, OpenPGP, or Yandex KMS envelope ([docs/README.md](https://github.com/wal-g/wal-g/blob/master/docs/README.md)).
- **Verification.** `wal-verify integrity|timeline` checks WAL continuity for PITR. `backup-push --verify` checks page checksums ([PostgreSQL.md](https://github.com/wal-g/wal-g/blob/master/docs/PostgreSQL.md)).
- **Licence and activity.** Apache-2.0 ([LICENSE.md](https://github.com/wal-g/wal-g/blob/master/LICENSE.md)). Releases on 2026-01-21, 2026-08-20 and 2026-11-17. The repo was pushed to on 2026-11-27.

### Barman

- **PG19 support: unconfirmed.** Neither the 3.21.0 release notes nor the user guide mention PostgreSQL 19. The docs mention PostgreSQL 18 behaviour for `verify-backup` ([RELNOTES.md](https://github.com/EnterpriseDB/barman/blob/release/3.21.0/RELNOTES.md), [verify_backup](https://github.com/EnterpriseDB/barman/blob/release/3.21.0/docs/user_guide/commands/barman/verify_backup.inc.rst)).
- **Deploy shape.** A dedicated Barman server (Python 3.12 to 3.14, rsync ≥ 3.1.0) ([installation](https://github.com/EnterpriseDB/barman/blob/release/3.21.0/docs/user_guide/installation.rst)). `backup_method` can be `rsync` over SSH (the default), `postgres` (pg_basebackup), `local-rsync` or `snapshot` ([configuration](https://github.com/EnterpriseDB/barman/blob/release/3.21.0/docs/user_guide/configuration.rst)). WAL arrives through `pg_receivewal` streaming or archiving. Streaming backup "makes life easier when working with Docker" ([architectures](https://github.com/EnterpriseDB/barman/blob/release/3.21.0/docs/user_guide/architectures.rst)). Over streaming, Barman needs no binary inside the postgres container, but it does need the replication hba entry from §2. A separate `barman-cloud-*` client targets S3, Azure and GCS ([barman_cloud](https://github.com/EnterpriseDB/barman/blob/release/3.21.0/docs/user_guide/barman_cloud.rst)). The repo's only Dockerfile builds the docs ("There is no other use for it"), so no official runtime image was found. Alpine has 3.19.1 in edge/testing only ([edge](https://pkgs.alpinelinux.org/packages?name=barman&branch=edge&arch=x86_64)).
- **Incremental.** PostgreSQL 17+ native incremental since Barman 3.11.0 ([RELNOTES.md](https://github.com/EnterpriseDB/barman/blob/release/3.21.0/RELNOTES.md)). rsync file reuse is also available.
- **Retention.** `retention_policy = REDUNDANCY n | RECOVERY WINDOW OF n DAYS|WEEKS|MONTHS`, plus `minimum_redundancy` ([retention_policies](https://github.com/EnterpriseDB/barman/blob/release/3.21.0/docs/user_guide/retention_policies.rst)).
- **PITR.** `--target-time`, `-xid`, `-lsn`, `-name` and `-immediate` ([recovery](https://github.com/EnterpriseDB/barman/blob/release/3.21.0/docs/user_guide/recovery.rst)).
- **Encryption.** `encryption = gpg` for backups and WAL ([configuration](https://github.com/EnterpriseDB/barman/blob/release/3.21.0/docs/user_guide/configuration.rst)).
- **Verification.** `barman check`. `check-backup` confirms the required WAL is archived. `verify-backup` runs `pg_verifybackup` and does not support encrypted backups ([commands](https://github.com/EnterpriseDB/barman/tree/release/3.21.0/docs/user_guide/commands/barman)).
- **Licence and activity.** GPL-3.0-or-later ([README](https://github.com/EnterpriseDB/barman/blob/release/3.21.0/README.rst)). Five releases between 2026-05-20 and 2026-11-18.

## 4. Restore verification guidance

- **PostgreSQL.** `pg_verifybackup` is not sufficient: "you should still perform test restores and verify that the resulting databases work as expected and that they appear to contain the correct data" ([app-pgverifybackup](https://www.postgresql.org/docs/19/app-pgverifybackup.html)). Test archiving before the first base backup, keep several backup sets, and inspect recovered data before letting users back in ([continuous-archiving](https://www.postgresql.org/docs/19/continuous-archiving.html)). For dumps, restore with `ON_ERROR_STOP` or `--single-transaction` into a database created from `template0`, then run `ANALYZE` ([backup-dump](https://www.postgresql.org/docs/19/backup-dump.html)). `pg_restore --exit-on-error` and `--list` support scripted checks ([app-pgrestore](https://www.postgresql.org/docs/19/app-pgrestore.html)).
- **pgBackRest.** `check` covers configuration and archiving, and `verify` checks repository validity ([command](https://pgbackrest.org/command.html)). The user guide mentions restore testing only when comparing repositories: "Only restore testing can determine which repository will be most efficient" ([user guide](https://pgbackrest.org/user-guide.html)).
- **WAL-G.** `wal-verify integrity` confirms that the WAL range from the oldest backup is present for PITR ([PostgreSQL.md](https://github.com/wal-g/wal-g/blob/master/docs/PostgreSQL.md)). No restore-test procedure was found in its docs.
- **Barman.** `check-backup` runs automatically after each backup and from cron. `verify-backup` delegates to `pg_verifybackup` ([commands](https://github.com/EnterpriseDB/barman/tree/release/3.21.0/docs/user_guide/commands/barman)).
- **Repo practice today.** The interim runbook restores the dump into a fresh PG19 target and checks it before proceeding ([runbook](../deployment/POSTGRES_19_MAJOR_UPGRADE_RUNBOOK.md)).

## 5. Redis: `noeviction` and persistence

Current Compose settings for both dev and prod are `maxmemory 256mb`, `maxmemory-policy noeviction`, `save 900 1 / 300 10 / 60 10000`, `appendonly yes`, and `./data/redis:/data` ([docker-compose.prod.yml](../../docker-compose.prod.yml)). ERP2 sends `PING` and reads `INFO`. It creates no Redis keys and stores its monitoring data in PostgreSQL ([Redis runbook](../deployment/REDIS_MEMORY_PRESSURE_RUNBOOK.md)).

- **`noeviction`.** "Keys are not evicted but the server will return an error when you try to execute commands that cache new data … commands that only read existing data still work" ([eviction](https://redis.io/docs/latest/develop/reference/eviction/)). It is the default ([redis.conf 8.6.8](https://github.com/redis/redis/blob/8.6.8/redis.conf)). The eviction page frames the eviction policies around caching, where entries "are copies of persistently-stored data". `allkeys-lru` is "a good default option" for caches. Reserving RAM for replication and AOF buffers below `maxmemory` "is not necessary for the `noeviction` policy" ([eviction](https://redis.io/docs/latest/develop/reference/eviction/)).
- **RDB snapshots** suit backups and disaster recovery. They lose "the latest minutes of data" on an unclean stop, and they need `fork()` ([persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)). With a save point configured, Redis by default stops accepting writes if the last background save failed (`stop-writes-on-bgsave-error yes`) ([redis.conf 8.6.8](https://github.com/redis/redis/blob/8.6.8/redis.conf)). The default save points are `3600 1 300 100 60 10000`, which differ from ERP2's `900 1 300 10 60 10000`.
- **AOF** with the default `appendfsync everysec` risks about 1 second of writes. AOF files are usually larger than RDB files. The docs recommend using both "if you want a degree of data safety comparable to what PostgreSQL can provide" and discourage AOF alone ([persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)). AOF is off by default (`appendonly no`) ([redis.conf 8.6.8](https://github.com/redis/redis/blob/8.6.8/redis.conf)).
- **No persistence.** "You can disable persistence completely. This is sometimes used when caching" ([persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)).
- **What the docs don't settle.** None of these pages covers a Redis that holds no application data, as ERP2's does once the queue is gone. The documented trade-offs are durability of keys against fork, disk and latency cost. Whether that durability has any value here depends on whether anything ever writes keys.

## 6. Docker official image guidance

- **PGDATA and volume layout.** From 18 onwards, `PGDATA` is version-specific (`/var/lib/postgresql/19/docker`) and the `VOLUME` is `/var/lib/postgresql`, so "users upgrading between PostgreSQL major releases [can] use the faster `--link` when running `pg_upgrade`" ([image docs](https://github.com/docker-library/docs/blob/master/postgres/content.md)). ERP2 already mounts `./data/postgres:/var/lib/postgresql` ([docker-compose.prod.yml](../../docker-compose.prod.yml)).
- **No backup guidance.** The image docs contain no section or mention of backups (0 occurrences of "backup") ([image docs](https://github.com/docker-library/docs/blob/master/postgres/content.md)).
- **Major upgrades are not automated.** The long-standing issue "Upgrading between major versions?" is still open ([docker-library/postgres#37](https://github.com/docker-library/postgres/issues/37)).
- **Initialisation.** `/docker-entrypoint-initdb.d` scripts and `POSTGRES_INITDB_ARGS` take effect only on an empty data directory. The docs still show `--data-checksums` as an opt-in example, although it has been the initdb default since 18 ([image docs](https://github.com/docker-library/docs/blob/master/postgres/content.md), [release-18](https://www.postgresql.org/docs/18/release-18.html)).
- **Configuration.** Use a custom config file or `-c` flags. The sample config lives at `/usr/local/share/postgresql/postgresql.conf.sample` on Alpine. The default `/dev/shm` of 64 MB may need `shm_size` ([image docs](https://github.com/docker-library/docs/blob/master/postgres/content.md)). Settings such as `archive_mode` and `summarize_wal` would go through one of these routes.

## Options this opens or closes

- **Logical-only, built-in.** `pg_dump -Fc` (or `-Fd -j`) plus `pg_dumpall --globals-only` from the existing `postgres:19.0-alpine3.24` sidecar pattern, with a scratch-container restore as the test. This needs no new image or hba change. It is the dump path, so there is no PITR: the recovery point is the last dump.
- **Physical, built-in.** Sidecar `pg_basebackup` with optional incremental backups and `pg_verifybackup`. This needs a replication hba entry and a replication role. PITR additionally needs `archive_mode`/`archive_command` running **inside** the postgres container, with WAL-archive monitoring, because of the PANIC-on-full `pg_wal` risk. Incremental chains have to be tracked by the design itself.
- **pgBackRest or WAL-G.** Both need their binary inside the postgres container for `archive_command`, which means a custom image. Neither has a stable Alpine 3.24 package with PG19 support, and neither states PG19 GA support yet.
- **Barman.** Runs beside PostgreSQL over streaming replication without changing the postgres image. It is a Python service with no official image, and PG19 support is unconfirmed.
- **App-managed backups in the Node image.** Closed for now. No PG19 client exists in stable Alpine 3.24 (edge/testing only), and an 18 client refuses to dump a 19 server.

## Off-host object storage providers

**Checked on:** 2026-11-28. Sources are each provider's own documentation, pricing pages and API references, the AWS S3 docs for reference semantics, and the AWS price list API for AWS rates. Where a page carries a `stale` marker or an old date, that is noted.

Context for the questions: one encrypted backup of a few MB (growing) every 30 minutes. The backend expires backups with a plain S3 `DeleteObject` (no `versionId`), which creates delete markers. The design needs versioning plus Object Lock with about 14 days of default retention, a production credential that cannot permanently delete versions or change bucket protection, a lifecycle rule that removes noncurrent versions N days after they become noncurrent, and a way to recover a version hidden by a delete marker.

### AWS S3 (reference semantics)

- **Object Lock.** Two modes. In compliance mode a locked version "can't be overwritten or deleted by any user, including the root user". In governance mode a user needs `s3:BypassGovernanceRetention` **and** the `x-amz-bypass-governance-retention:true` header ([object-lock](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html)). A bucket default retention can be set in days or years ([object-lock](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html)). AWS has also added *variable retention* (event holds), which this design does not need ([object-lock-configure](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock-configure.html)). Object Lock can be enabled on an existing bucket through `PutObjectLockConfiguration` (`aws s3api put-object-lock-configuration … '{"ObjectLockEnabled":"Enabled","Rule":{"DefaultRetention":{"Mode":…,"Days":…}}}'`). "After you enable Object Lock on a bucket, you can't disable Object Lock or suspend versioning" ([object-lock-configure](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock-configure.html)).
- **Delete markers under lock.** A simple `DELETE` without a version ID on a locked object returns `200 OK` and inserts a delete marker. A `DELETE` with a version ID returns `403` ([object-lock](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html)). "Delete markers are not WORM-protected, regardless of any retention period or legal hold in place on the underlying object" ([object-lock-managing](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock-managing.html)).
- **Credential scoping: delete marker vs. permanent delete.** These are different IAM actions. The permissions table says `s3:DeleteObject` is "Required if you want to remove an object without specifying `versionId`" and `s3:DeleteObjectVersion` is "Required if you want to remove a specific version". Governance-locked versions additionally need `s3:BypassGovernanceRetention` ([using-with-s3-policy-actions](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-with-s3-policy-actions.html)). The `DeleteObject` API page words it differently: "you must always have the `s3:DeleteObject` permission", plus `s3:DeleteObjectVersion` for a specific version ([API_DeleteObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_DeleteObject.html)). Under either wording, a principal without `s3:DeleteObjectVersion` cannot permanently delete a version. Other relevant actions from the same table: `PutObject` → `s3:PutObject` (plus `s3:PutObjectRetention` only to set explicit retention); `GetObject` → `s3:GetObject`, or `s3:GetObjectVersion` when a `versionId` is given; `ListObjectsV2` → `s3:ListBucket`; `ListObjectVersions` → `s3:ListBucketVersions`; `PutObjectLockConfiguration` → `s3:PutBucketObjectLockConfiguration`; `PutBucketVersioning` → `s3:PutBucketVersioning`; lifecycle put and delete → `s3:PutLifecycleConfiguration` ([using-with-s3-policy-actions](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-with-s3-policy-actions.html)). Any user with `s3:PutObjectRetention` can extend a retention period ([object-lock](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html)). Shortening or removing governance retention needs the bypass permission ([object-lock-managing](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock-managing.html)).
- **Lifecycle.** `NoncurrentVersionExpiration` with `NoncurrentDays` removes noncurrent versions N days "after they become noncurrent". The optional `NewerNoncurrentVersions` keeps 1 to 100 versions, and both conditions must be exceeded for deletion. `ExpiredObjectDeleteMarker` removes delete markers that have no remaining versions. Lifecycle is set through the S3 API (`PutBucketLifecycleConfiguration`) ([lifecycle-configuration-examples](https://docs.aws.amazon.com/AmazonS3/latest/userguide/lifecycle-configuration-examples.html)). With Object Lock: "a locked version of an object cannot be deleted by a S3 Lifecycle expiration policy", while lifecycle still places delete markers ([object-lock-managing](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock-managing.html)). The docs do not say when lifecycle removes a version after its lock lapses. Unconfirmed.
- **Recovering a version hidden by a delete marker.** List with `aws s3api list-object-versions` (the `DeleteMarkers` and `Versions` arrays) ([ManagingDelMarkers](https://docs.aws.amazon.com/AmazonS3/latest/userguide/ManagingDelMarkers.html)). There are three ways back. (1) Delete the marker with `DeleteObject` plus the marker's `versionId`. This is a versioned delete, so it needs `s3:DeleteObjectVersion` ([ManagingDelMarkers](https://docs.aws.amazon.com/AmazonS3/latest/userguide/ManagingDelMarkers.html), [policy actions](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-with-s3-policy-actions.html)). (2) Copy the old version in place with `aws s3api copy-object --copy-source bucket/key?versionId=…`, which needs `s3:GetObjectVersion` on the source and `s3:PutObject` ([RestoringPreviousVersions](https://docs.aws.amazon.com/AmazonS3/latest/userguide/RestoringPreviousVersions.html), [policy actions](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-with-s3-policy-actions.html)). (3) Read it directly with `GetObject` plus `versionId`, which needs `s3:GetObjectVersion`.
- **Costs (us-east-1, AWS price list version `20261125152611`).** S3 Standard costs $0.023/GB-month for the first 50 TB. PUT, COPY, POST and LIST cost $0.005 per 1,000. GET and all other requests cost $0.004 per 10,000 ([price list API](https://pricing.us-east-1.amazonaws.com/offers/v1.0/aws/AmazonS3/current/us-east-1/index.json)). "DELETE and CANCEL requests are free". S3 Standard has no minimum storage duration; minimums apply only to IA and Glacier classes ([s3/pricing](https://aws.amazon.com/s3/pricing/)). Internet egress is free for the first 100 GB per month aggregated globally, then $0.09/GB for the first 10 TB ([AWSDataTransfer price list](https://pricing.us-east-1.amazonaws.com/offers/v1.0/aws/AWSDataTransfer/current/us-east-1/index.json)). New accounts get "up to $200 in AWS Free Tier credits" (since 2025-07-15) instead of a fixed S3 allowance ([s3/pricing](https://aws.amazon.com/s3/pricing/)). Whether lifecycle expirations are billed is not stated on the pricing page. Unconfirmed.
- **SDK and CLI behaviour.** Current AWS SDKs and the AWS CLI compute a checksum on every upload by default (`request_checksum_calculation` / `AWS_REQUEST_CHECKSUM_CALCULATION`, default `WHEN_SUPPORTED`, alternative `WHEN_REQUIRED`) and validate response checksums by default. The default algorithm is CRC32 for SDK for JavaScript 3.x and CRC64NVME for AWS CLI v2 ([feature-dataintegrity](https://docs.aws.amazon.com/sdkref/latest/guide/feature-dataintegrity.html)). An upload "with a retention period configured using Object Lock" needs `Content-MD5` or `x-amz-sdk-checksum-algorithm` ([object-lock-managing](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock-managing.html)). Every non-AWS provider below therefore has to accept the SDK's default checksum headers or trailers, or the client must be set to `WHEN_REQUIRED`.

### Backblaze B2

- **Object Lock.** Governance and compliance modes, plus legal hold. Default bucket retention is supported, at 1 to 3,000 days, and applies to files uploaded after it is set. Object Lock can be enabled "when you create a bucket, or … on an existing bucket", through the console, Native API (`b2_update_bucket`), S3-Compatible API, SDKs or CLI, and "you cannot disable this setting" afterwards ([cloud-storage-object-lock](https://www.backblaze.com/docs/cloud-storage-object-lock)). The same page also says "You must enable Object Lock when you create a bucket to configure default bucket retention settings", which contradicts the existing-bucket statement. The [existing-bucket guide](https://www.backblaze.com/docs/cloud-storage-enable-object-lock-or-a-legal-hold-on-an-existing-bucket) shows only console steps. The S3 `PutObjectLockConfiguration` reference shows a GOVERNANCE, 14-day default rule, but that page is marked `stale: true` (2023-05-31) and does not say whether it can enable lock on an existing bucket ([s3-put-object-lock-configuration](https://www.backblaze.com/apidocs/s3-put-object-lock-configuration)). Enabling lock on an existing bucket **through the S3 API** is therefore unconfirmed. S3 `PutObject` accepts `x-amz-object-lock-mode` (GOVERNANCE or COMPLIANCE), `-retain-until-date` and `-legal-hold` ([s3-put-object](https://www.backblaze.com/apidocs/s3-put-object), dated 2023-06-01).
- **Versioning.** "Buckets in Backblaze B2 are versioned by default" ([intro to S3 API](https://www.backblaze.com/apidocs/introduction-to-the-s3-compatible-api)). S3 `DeleteObject` without a version ID inserts "a delete marker [that] will become the current version". With a version ID, the object "will be permanently deleted" ([s3-delete-object](https://www.backblaze.com/apidocs/s3-delete-object), marked `stale: true`). Natively, a delete marker is a hide marker (`b2_hide_file`) ([file versions](https://www.backblaze.com/b2/docs/file_versions.html)).
- **Credential scoping.** Capabilities ([application-key-capabilities](https://www.backblaze.com/docs/cloud-storage-application-key-capabilities), [S3 app keys](https://www.backblaze.com/docs/cloud-storage-s3-compatible-app-keys)):
  - `writeFiles`: upload, including `b2_hide_file`. "The `writeFiles` permission is necessary when you delete a file by name."
  - `deleteFiles`: `b2_delete_file_version`. "The `deleteFiles` permission is required when you delete a specific version."
  - `readFiles`: Get/Head/Copy Object.
  - `listFiles`: List Objects, List Objects V2, List Object Versions.
  - `bypassGovernance`: delete governance-locked files, shorten governance retention, or switch to compliance.
  - `writeFileRetentions`: Put Object Retention.
  - `writeBucketRetentions`: create lock-enabled buckets and change default lock settings, including Put Object Lock Configuration.
  - `writeBuckets`: lifecycle and Put Bucket Versioning. It is "not allowed for the app keys that are restricted to a bucket".
  - `writeBucketLifecycleRules`: Put and Delete Lifecycle Configuration. This name appears on the S3 app-keys page but not on the capabilities list.

  So a bucket-restricted key with `listFiles`, `readFiles` and `writeFiles`, and without `deleteFiles`, `bypassGovernance`, `writeFileRetentions`, `writeBucketRetentions` or the lifecycle capabilities, matches the capability descriptions. The same S3 page says "you should include both the `writeFiles` and `deleteFiles` capabilities for the Delete Object and Delete Objects calls". **Whether a by-name S3 `DeleteObject` succeeds without `deleteFiles` is unconfirmed.** No page states it outright.
- **Lifecycle.** Native rules use `daysFromHidingToDeleting` (for example, "the older version is deleted 10 days after you upload a newer version") and `daysFromUploadingToHiding`, with positive days only and up to 100 rules. Rules run "once per day". "If the file version to which the rule applies has Object Lock enabled, then the deletion does not occur" ([lifecycle-rules](https://www.backblaze.com/docs/cloud-storage-lifecycle-rules)). Through the S3 API, `PutBucketLifecycleConfiguration` supports `NoncurrentVersionExpiration`/`NoncurrentDays` (mapped to the B2 "delete" action), `Expiration` `Days`, `ExpiredObjectDeleteMarker=true`, `AbortIncompleteMultipartUpload` and `Filter`/`Prefix`. It rejects `NewerNoncurrentVersions`, date expiration, `Status=Disabled`, tag or size filters and overlapping prefixes ([s3-put-lifecycle-configuration](https://www.backblaze.com/apidocs/s3-put-lifecycle-configuration)). A different page still says "Lifecycle Rules are currently available only through the Backblaze web console and the Native API" ([S3 bucket versions](https://www.backblaze.com/docs/cloud-storage-s3-compatible-api-bucket-versions)). The docs conflict here.
- **Recovering a hidden version.** Use S3 `ListObjectVersions` (`listFiles`) and `GetObject` with a version (`readFiles`). Natively, "you can also delete the marker that indicates that a file is hidden", and "deleting a file version cannot be undone" ([file versions](https://www.backblaze.com/b2/docs/file_versions.html)). Deleting the marker is a version delete, so it needs `deleteFiles` (inference from the capability table). The B2 CLI has `b2 file unhide` ([B2 CLI blog](https://www.backblaze.com/blog/command-like-a-pro-with-new-backblaze-b2-cli-enhancements/)). Whether S3 `CopyObject` with a source `versionId` is supported is not described ([s3-copy-object](https://www.backblaze.com/apidocs/s3-copy-object)). Unconfirmed.
- **Costs.** "$6.95/TB/30-days", billed per byte-hour. "First 10GB storage is always free". "No minimum file size fees" and "No minimum storage duration fees". Class A, B and C calls are free for pay-as-you-go. Only Class D (outbound, such as event notifications) is charged, at $0.004 per 10,000 after 2,500 free per day. Egress is free up to 3× average monthly stored data, then $0.01/GB ([pricing](https://www.backblaze.com/cloud-storage/pricing), [transaction pricing](https://www.backblaze.com/cloud-storage/transaction-pricing)). Object Lock has "no extra cost" ([object-lock](https://www.backblaze.com/docs/cloud-storage-object-lock)).
- **S3 compatibility caveats.** The master application key cannot use the S3 API. ACLs, IAM roles, object tagging, website configuration and SSE-KMS are unsupported ([intro to S3 API](https://www.backblaze.com/apidocs/introduction-to-the-s3-compatible-api), [S3-compatible API](https://www.backblaze.com/docs/cloud-storage-s3-compatible-api)). `x-amz-sdk-checksum-algorithm` must be accompanied by an `x-amz-checksum` or `x-amz-trailer` header ([s3-put-bucket-logging](https://www.backblaze.com/apidocs/s3-put-bucket-logging)). Copies keep checksum data, but CopyObject cannot change the algorithm ([s3-copy-object](https://www.backblaze.com/apidocs/s3-copy-object)). Whether B2 accepts the SDK's default CRC32 `aws-chunked` trailer on `PutObject` is not documented on the `PutObject` page. Unconfirmed.

### Cloudflare R2

- **Versioning: not supported.** `PutBucketVersioning` and `GetBucketVersioning` are listed as unimplemented. There is therefore no delete marker, no noncurrent version and no `ListObjectVersions` (not mentioned) ([R2 S3 API compatibility](https://developers.cloudflare.com/r2/api/s3/api/)).
- **Object Lock: not supported through the S3 API.** `PutObjectLockConfiguration` and `GetObjectLockConfiguration` are unimplemented. The `x-amz-object-lock-*` headers on PutObject, CopyObject and CreateMultipartUpload, `x-amz-bucket-object-lock-enabled` and `x-amz-bypass-governance-retention` are all unsupported ([R2 S3 API compatibility](https://developers.cloudflare.com/r2/api/s3/api/)). R2 has its own **bucket locks** instead: prefix rules with an age, a date or indefinite retention, managed through the dashboard, `wrangler r2 bucket lock` or the Cloudflare API. They cover existing and new objects and block overwrites and deletes. There are no governance or compliance modes, and a rule can be removed by anyone who can edit bucket configuration ([bucket-locks](https://developers.cloudflare.com/r2/buckets/bucket-locks/)). Because there is no versioning, a locked key also cannot be overwritten or deleted by the backend's own expiry until its lock ends. That is an inference from the docs.
- **Credential scoping.** Token levels are Admin Read & Write ("create, list, and delete buckets, edit bucket configuration"), Admin Read only, Object Read & Write ("read, write, and list objects in specific buckets"), and Object Read only. Only the object levels can be scoped to buckets ([R2 tokens](https://developers.cloudflare.com/r2/api/tokens/)). The docs don't say whether Object Read & Write includes `DeleteObject`, and they offer no write-without-delete level. Unconfirmed. Without versioning, any successful delete is permanent.
- **Lifecycle.** Expire after N days or on a date, transition to Infrequent Access, and abort multipart uploads. It is configurable through the S3 API (`PutBucketLifecycleConfiguration`), the dashboard or Wrangler. Objects are "typically … removed … within 24 hours". There is no noncurrent-version concept ([object-lifecycles](https://developers.cloudflare.com/r2/buckets/object-lifecycles/)). Bucket locks take precedence over lifecycle deletion ([bucket-locks](https://developers.cloudflare.com/r2/buckets/bucket-locks/)).
- **Costs.** Standard costs $0.015/GB-month, Class A $4.50 per million and Class B $0.36 per million. The free tier per month is 10 GB-month, 1 M Class A and 10 M Class B. Egress is free. Standard has no minimum duration (IA has 30 days). DeleteObject is free. PutObject and ListObjects are Class A, and GetObject and HeadObject are Class B. ListObjectsV2 is not named ([R2 pricing](https://developers.cloudflare.com/r2/pricing/)).
- **S3 compatibility caveats.** `ListObjectsV2` is implemented. Checksums: CRC-64/NVME is supported as FULL_OBJECT. CRC-32, CRC-32C, SHA-1 and SHA-256 are supported only as COMPOSITE ([R2 S3 API compatibility](https://developers.cloudflare.com/r2/api/s3/api/)).

### Wasabi

- **Object Lock.** Governance mode can be bypassed by the root user or "any user who has the IAM permission `s3:BypassGovernanceRetention`". Compliance mode "cannot be reversed for any reason, by any user". Legal hold is also supported. Default bucket retention is optional, in days or years, and applies only to new objects. "Object lock can be enabled only while creating the bucket", it requires versioning, and it cannot be disabled. A lock-enabled bucket cannot also use Wasabi's separate bucket-level "Compliance" feature ([object-locking](https://docs.wasabi.com/docs/object-locking), [object-locking-enable](https://docs.wasabi.com/docs/object-locking-enable)). Through the S3 API, the docs show `aws s3api create-bucket --object-lock-enabled-for-bucket` and a `PUT ?object-lock` with `ObjectLockEnabled`, a mode and Days or Years ([AWS CLI with Wasabi](https://docs.wasabi.com/docs/how-do-i-use-aws-cli-with-wasabi), [Object Lock on buckets API](https://docs.wasabi.com/apidocs/object-lock-on-buckets-with-the-wasabi-s3-api)).
- **Credential scoping.** Policies use AWS IAM JSON (`Version`/`Statement`/`Effect`/`Action`/`Resource`, `arn:aws:s3:::…`) attached to users ([creating-a-policy](https://docs.wasabi.com/docs/creating-a-policy)), and Wasabi describes itself as compatible "with the AWS S3 and IAM APIs" ([Wasabi S3 API reference](https://docs.wasabi.com/apidocs/wasabi-api)). Deleting governance-locked versions needs `s3:BypassGovernanceRetention` plus the bypass header ([deleting object versions](https://docs.wasabi.com/docs/how-do-i-delete-old-object-versions)). No Wasabi page found states that `s3:DeleteObject` and `s3:DeleteObjectVersion` are enforced separately as on AWS, and no full action list was found. **Unconfirmed.** Checked: creating-a-policy, deleting object versions, the llms.txt index, and the S3 API reference introduction.
- **Lifecycle.** The console offers "permanently delete noncurrent versions" N days after they become noncurrent, with optional newer versions to keep, plus expire current versions, delete expired delete markers (not combinable with expire-current) and abort incomplete multipart uploads (default 31 days) ([lifecycle](https://docs.wasabi.com/docs/lifecycle)). The AWS CLI guide shows `put-bucket-lifecycle-configuration` with `NoncurrentVersionExpiration`/`NoncurrentDays` ([lifecycle via AWS CLI](https://docs.wasabi.com/docs/how-to-set-lifecycle-policies-using-the-aws-cli)). No Wasabi page found covers how lifecycle interacts with locked versions. Unconfirmed.
- **Recovering a hidden version.** `aws s3api list-object-versions --endpoint-url https://s3.<region>.wasabisys.com` returns `DeleteMarkers` and versions. Deletion of a specific version is done with `delete-object --version-id` ([deleting object versions](https://docs.wasabi.com/docs/how-do-i-delete-old-object-versions)). That page does not state that removing a marker restores the object, although that is the AWS semantics.
- **Costs.** Pay-as-you-go costs $7.99/TB/month from 2026-07-01 ([May 2026 pricing notice](https://docs.wasabi.com/docs/may-2026-wasabi-pricing.md)). **Minimum storage duration is 90 days (confirmed).** Deleting earlier incurs "a Timed Deleted Storage charge equal to the storage charge for the remaining days". There is also a 4 KB minimum billable object size, a minimum monthly charge equal to 1 TB of active storage, no API request charges, and free egress while monthly egress is "less than or equal to your active storage volume" ([pricing FAQ](https://wasabi.com/pricing/faq)). Whether noncurrent versions or overwrites count as deletions for the 90-day rule is not stated ([90-day policy](https://docs.wasabi.com/docs/if-i-delete-a-file-within-90-days-after-storing-it-how-is-that-handled-from-a-billing-and-file-recovery-perspective.md)). Unconfirmed.
- **S3 compatibility caveats.** Requests must use the bucket's regional endpoint, and with the wrong endpoint reads still work but writes and deletes fail ([Wasabi S3 API reference](https://docs.wasabi.com/apidocs/wasabi-api)). "Additional checksums" support CRC (CRC-32C named) and SHA-256 families, with CRC64NVME through the CLI and API only. Pre-calculated checksums work only for single objects under 96 MB, and MD5 is applied by default ([additional checksums](https://docs.wasabi.com/docs/additional-checksums.md), 2025-12-30). Behaviour with the SDK's default `aws-chunked` CRC32 trailer is not documented. Unconfirmed. `ListObjectsV2` support is not stated on any page found. Unconfirmed.

### Cost estimate

Assumptions: 1 GB = 1,000 MB and a 30-day month. Retained current backups are 50 × 20 MB = 1.0 GB. Expired uploads stay as noncurrent versions for 14 to 30 days: 48/day × 20 MB = 0.96 GB/day, so 13.4 to 28.8 GB. Total stored is about **14.4 to 29.8 GB**. Requests per month: 1,440 `PutObject`, 1,440 `DeleteObject` and roughly 1,440 `ListObjectsV2` (one per run). GETs and restore-test egress are small enough to stay inside every provider's free egress allowance.

### Healthchecks.io

- **Free tier.** The Hobbyist plan ($0) is "Monitor 20 jobs, 100 log entries per job". SMS, WhatsApp and phone-call credits appear only on Business ($20/month: 100 jobs, 50 SMS and WhatsApp, 20 calls) and Business Plus ([pricing](https://healthchecks.io/pricing/)). Companies may use Hobbyist commercially, but Healthchecks.io expects them "to eventually upgrade" ([FAQ](https://healthchecks.io/faq/)). No limit on the number of notification integrations, or on team members, is stated on the pricing page or the docs checked. Unconfirmed. Integrations belong to a project ([configuring notifications](https://healthchecks.io/docs/configuring_notifications/)).
- **Period and Grace.** Period "is the expected time between pings". Grace Time "is the additional time to wait before sending an alert when a check is late" ([configuring checks](https://healthchecks.io/docs/configuring_checks/)). A simple-schedule check is Late once the period has passed since the last ping, and Down (alerts sent) once the period plus grace has passed. For example, with a 1 h period, 5 min grace and last ping at 12:00, it is late at 13:00 and down at 13:05 ([docs intro](https://healthchecks.io/docs/)). After a `/start` signal, success is expected within Grace Time, or the check fails ([configuring checks](https://healthchecks.io/docs/configuring_checks/)). Cron and OnCalendar schedules are also available.
- **Alert repetition.** "The Healthchecks.io alerts are 'one-shot'". Repeats come only from integrations such as PagerDuty or Pushover Emergency, or from optional hourly or daily email reminders while any check is down ([FAQ](https://healthchecks.io/faq/), [configuring notifications](https://healthchecks.io/docs/configuring_notifications/)). The email integration has separate `down` and `up` toggles, both on by default ([source: hc/integrations/email/forms.py](https://github.com/healthchecks/healthchecks/blob/master/hc/integrations/email/forms.py)). So by default one email is sent when a check goes down and one when it recovers.
- **Ping URLs.** The forms are `https://hc-ping.com/<uuid>`, plus `/start`, `/fail`, `/log` and `/<exit-status>` (0 to 255, where 0 means success and non-zero means failure). Slug variants take the form `https://hc-ping.com/<ping-key>/<slug>[/…]`. HEAD, GET and POST are accepted, and POST bodies are stored up to the first 100 kB when they look like UTF-8 text. The optional `?rid=<uuid>` pairs start and completion pings ([pinging API](https://healthchecks.io/docs/http_api/), [signaling failures](https://healthchecks.io/docs/signaling_failures/)). `/fail` "Signals to Healthchecks.io that the job has failed", so the alert goes out without waiting for the schedule to lapse ([pinging API](https://healthchecks.io/docs/http_api/)).
