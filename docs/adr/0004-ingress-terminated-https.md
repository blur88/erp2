# Production HTTPS terminates at the Ingress, under one canonical hostname, with host-managed certificates

In production the Ingress (ADR 0003) owns the public HTTPS listener. It publishes `443` and terminates TLS itself, so it stays the only entry point. Its rate limits still see the client's address, `X-Forwarded-Proto $scheme` reports `https` to the backend without any proxy trust, and the security-header policy, HSTS included, stays in one place. Production is HTTPS-only. Development (`docker-compose.yml`, `./deploy.sh`) stays plain HTTP on `localhost`, with no certificate and no HSTS.

We decided this in #1960, the follow-up that ADR 0003 left open. The stock stack served only HTTP on port 80, and the Ingress sent HSTS over HTTP, where browsers ignore it.

How it works:

- **One image, two configs.** `nginx.conf` is the HTTP-only development config. `nginx-https.conf` is the production config, selected in `docker-compose.prod.yml` with `nginx -c`. Both share the locations and rate-limit zones through includes. The container stays `read_only`.
- **One canonical hostname.** `ERP_PUBLIC_HOST` is the only per-install input to the Ingress. Production Compose requires it, and an entrypoint check rejects anything that isn't a bare DNS hostname (no scheme, port, path, wildcard or IP literal) before templating runs. The stock nginx envsubst, filtered to that one variable, renders it into a tmpfs (`/etc/nginx/runtime`). The canonical `:443` server's `server_name` uses it. A default `:443` server presents the same certificate and answers `421` without forwarding upstream. `setup.sh` derives `FRONTEND_URL` and `ALLOWED_ORIGINS` as `https://<host>`, and its preflight fails if they disagree.
- **Port 80 only redirects and answers ACME.** `/.well-known/acme-challenge/` is served as static files from a read-only webroot mount (`${ACME_WEBROOT:-/var/lib/erp2/acme}`). Every other request gets a 301 to `https://<canonical host>$request_uri`, whatever `Host` it sent.
- **HSTS is `max-age=31536000; includeSubDomains`, without `preload`.** It is sent exactly once on canonical HTTPS responses, redirects included, and never on port 80 or a `421`. It lives in an HTTPS-only include, separate from the other security headers. Preload enrollment is left to the domain owner. Backend Helmet keeps its own HSTS settings for direct-backend use, and the Ingress hides that copy.
- **TLS.** Mozilla Intermediate profile, guidelines version 6.0 (primary source `https://data.tlsref.org/guidelines/6.0.json`, pinned with its checksum in `scripts/__tests__/fixtures/`): TLS 1.2 and 1.3, session tickets off, a shared session cache, HTTP/2 on `443`, no OCSP stapling (Let's Encrypt stopped running OCSP in 2025). Socket.IO WebSockets keep their HTTP/1.1 upgrade path.
- **Certificates are host-managed and copied, never bind-mounted from certbot.** The host directory `${TLS_DIR:-/etc/erp2/tls}` is mounted read-only at `/etc/nginx/tls`, holding fixed `fullchain.pem` and a root-owned `0600` `privkey.pem`. Certbot's `live/` files are symlinks into `archive/`. A mounted `live/<domain>` directory loses those targets, and a bind-mounted file pins the inode Docker saw at start, so a reload would keep serving the old certificate. The documented route is certbot on the host: standalone mode for the first certificate while port 80 is free, then `certbot reconfigure` to webroot renewals with a deploy hook generated by `./setup.sh tls-hook`. The hook acts only for the ERP lineage, stages the new pair in `TLS_DIR`, swaps it in, runs `nginx -t`, and then reloads or restores the previous pair. Bring-your-own certificates use the same layout.

## Considered Options

- **An external TLS proxy in front of an HTTP-only Ingress.** Rejected. Every client would arrive from the proxy's address, so the rate limits would need trusted `X-Forwarded-For` handling. The proxy would have to overwrite `X-Forwarded-Proto`, direct access to the Ingress would have to be closed, and HSTS would move out of the header policy.
- **Supporting both a proxy-fronted mode and Ingress termination.** Rejected. Twice the configuration to test and document, for a deployment nobody has asked for.
- **An HTTP-only production opt-out.** Rejected. It keeps a second production mode alive. Local HTTP remains available through `./deploy.sh`.
- **Bind-mounting the nginx config, or a host-generated redirect fragment, from the host.** Rejected. Production ships only `setup.sh` and `docker-compose.prod.yml`, and a host file drifts from the image or from `.env`.
- **Redirecting to `$host`, or serving any `Host` on `443`.** Rejected. Pages would be served under origins that CORS and `FRONTEND_URL` don't expect, and the redirect would follow whatever `Host` the client sent. Noncanonical HTTPS gets `421`, not a redirect.
- **Keeping `preload`.** Rejected. It consents to hardcoding the domain into browsers, removal takes months, anyone can submit a domain that sends it, and ERP installs usually live on subdomains that can't be preloaded anyway.
- **Standalone certbot for every renewal.** Rejected. It means stopping the Ingress every ~60 days. DNS-01 needs a different plugin for each DNS provider, and documenting bring-your-own alone would leave most operators without a renewal path.

## Consequences

- **This is a breaking release for existing production installs.** The new Ingress won't start without `fullchain.pem` and `privkey.pem` in `TLS_DIR`. Operators provision and preflight the certificate first, following `docs/deployment/HTTPS_UPGRADE.md`, and if certbot standalone needs port 80 they plan an interruption to free it.
- **The HSTS commitment lasts one year**, and `includeSubDomains` covers every name under the canonical hostname, internal ones included. Those names must serve HTTPS before the policy goes live.
- **Changing `ERP_PUBLIC_HOST` means recreating the Ingress**, because the entrypoint renders it at container start.
- **Real Let's Encrypt issuance, renewal and the generated deploy hook are verified by hand** (`certbot renew --dry-run --run-deploy-hooks`). CI pins the Ingress behaviour with a test CA in `scripts/__tests__/ingress.test.js`, and the `setup.sh` preflight with shell-level tests.
- The rate limits still key on the connecting address. Behind any extra proxy an operator adds on their own, that is the proxy's address, as ADR 0003 already notes.
